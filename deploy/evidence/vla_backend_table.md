**No serving default.** demo/vla_server_v2.py refuses to load the model until --precision, --attn and --merge/--no-merge are all given, and every response's identity carries the chosen configuration's agreement with the reference. Which configuration flies is decided by measuring CityLife's own VRAM beside the model (next wave): the bf16 rows fit only if the renderer and OWL-ViT leave about 17 GB of the 24 GB card free.

**Low-VRAM option:** nf4/sdpa/merged (p50 517 ms, process VRAM 7.9 GB, agrees with the reference on 31% of 48 probe inputs). **Fidelity option:** bf16/sdpa/unmerged (p50 486 ms, process VRAM 16.8 GB, agrees with the reference on 96% of 48 probe inputs). Fastest overall: bf16/sdpa/merged. Rule: low-VRAM option = lowest p50 among configurations with p50 <= gate, no timed parse failure and process VRAM (vram_process_gb) <= vram_budget_gb; fidelity option = highest exact agreement with the reference among the other configurations with p50 <= gate and no timed parse failure; neither is a default (budget 10 GB, an assumption until CityLife's VRAM is measured).

Why there is no default, and what each option costs (decided 2026-10-22, review of V1a). The precision changes what the model says: bf16 reproduces the upstream-precision reference - bf16/sdpa/unmerged gives the reference's output on 96 % of the 48 probe inputs, the merged bf16 rows on 88-90 % (greedy near-ties) - while every nf4 row agrees on only 25-33 % exactly and 48-50 % within 3 bins; 4-bit quantisation, not the attention kernel or the merge, is what moves the outputs. On the no-hint phrase every bf16 row and both nf4 merged rows answer '00 49 49 LAND' on 5 of 6 frames, while the nf4 unmerged loader (the one every earlier AerialVLA script here used) reproduces two of the 4 Aug malformed landing outputs ('00 49 4949', '00 49 494 49'); the strict reader turns those into holds. nf4/sdpa/merged is kept as the measured low-VRAM option (p50 517 ms; about 7.9 GB held by the process, 5.4 GB of it allocated by torch), not as a default that silently changes behaviour. A bf16 process holds about 16.8-16.9 GB: bf16/sdpa/unmerged (p50 486 ms) is the closest to the reference, bf16/sdpa/merged the fastest (p50 259 ms, below the paper's 0.35 s; its nvidia-smi reading failed, so its process VRAM is not recorded). The 10 GB budget behind the low-VRAM rule is an assumption, not a measurement: the card has 24 GB, desktop applications held about 3.4 GB before the runs (one reading, subtracted from every row's nvidia-smi figure), OWL-ViT takes 0.61 GB, and CityLife's own VRAM has never been logged. Measuring CityLife's VRAM beside the model is what decides which configuration flies (next wave); until then the server loads none by default.

Over TCP (127.0.0.1, `demo/vla_server_v2.py ping`, nf4/sdpa/merged): round trip p50 539 ms, p95 581 ms against server latency_s p50 537 ms (n=50): the transport and JPEG frames add the difference.

These are the AerialVLA server's configurations, not the project's default backend: the grant defers that choice to the full measurement set, and the table above still says none. Every number is standalone; in flight the renderer shares the GPU (OWL-ViT's forward pass ran 13.8-21.5x slower in flight than offline: CHANGELOG 0.5.0, 2026-09-10, Known limitations), so these are the floor, not the flight rate.
